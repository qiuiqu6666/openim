# 群申请与处理人

## 群通知空状态

2026-10-07 群通知复用联系人模块 `empty/contact_list_placeholder.dart` 和公共 `IllustratedEmptyState`，成功空列表居中显示现有 `empty_99chat.webp` 与“暂无群通知”，支持亮暗主题、小屏滚动和英文。对照 99chat `all_group_application_list.dart:_buildNoticeList` 的状态语义，按用户要求升级为与“新的朋友”等页面相同的插画。

`applicationsLoaded` 仅在最新请求且当前账号/token 对应的 SDK 列表读取成功后设为 true；首屏等待显示页内加载，失败显示重试入口。有记录时继续使用原列表和 LoadingView，审批、处理人和资料获取流程不变。`reloadApplications` 处理页面/事件入口错误；直接调用 `getApplicationList` 的处理详情仍收到原 SDK 异常。错误状态和结果均检查请求代次及会话归属。

复用原资源、组件和翻译，无新增图片或数据接口。回归测试位于 `test/pages/contacts/group_requests/`；本次未重新生成安装包或进行真机验证。

列表及处理详情复用 `widgets/group_request_handler_label.dart`，在现有说明/状态下方显示本地化的“处理人：昵称”。使用现有弱文字主题样式，长昵称单行省略；缺少昵称时不占位，保留原处理状态与操作流程。

显示位置参考本地 99chat 仓库 `lib/src/all_group_application_list.dart` 的处理人弱文字行；数据仍使用当前 OpenIM SDK，不引入参考仓库的申请接口或用户 ID 回退。

处理人只来源于已同意或已拒绝记录的 `GroupApplicationInfo.handleUserID`。`GroupRequestsLogic` 将处理人和原有邀请人 ID 去重，使用现有 SDK `getUsersInfo` 批量查询公开昵称。不把申请人、邀请人、当前登录管理员或用户 ID 当作处理人昵称。旧记录没有处理人 ID，或资料不可用时不显示该行；资料查询失败不会丢弃申请列表。

成功审批先保持已完成状态，再拉取真实记录以获取处理人；服务端尚未返回完成记录时不猜测处理人，也不重新开放按钮。若 SDK 返回申请已被他人处理，则采用刷新记录中的实际结果和处理人。详情通过原请求的群 ID、申请人 ID、申请时间匹配列表，响应已有群申请变更订阅。

查询结果检查请求代次、所属账号与登录 token，关闭页面取消订阅；详情在实际提交及异步返回时检查会话归属，避免旧页面在切换账号后更新状态。没有新增后端接口或登录凭证输出。

测试归属 `test/pages/contacts/group_requests/`，使用 SDK 通道替身验证真实字段映射、批量查询、处理后刷新、多人管理回调及异步保护。实际服务器对多个管理员的回调广播和处理人字段完整性仍需真实登录联调。

2026-10-05 验证：本工作区模块及测试静态检查通过，昵称组件的 5 项测试通过。隔离验证副本使用与工作区相同的本次实现，22 项相关测试全部通过，包含真实列表在亮暗主题下的昵称更新、缺失资料、状态/按钮保留及溢出检查。原工作区完整模块测试被并行群功能改动中的 `GroupFeatureStore.cachedGroupInfo` 缺失阻塞，未修改该无关模块。

## 历史记录缺少处理人

2026-10-05 从已连接模拟器的当前应用日志核对用户截图中的历史申请：请求时间 `1790878326865`、已同意，申请人/群名/理由均与截图匹配。SDK 返回的 `handleUserID` 为空，`handledTime` 为 0；该现象在两次读取中一致。因此该条记录无法查询处理人昵称，并非客户端凭现有数据可以自动补齐的字段。这里只确认当前 SDK 返回值，未直接查询部署服务器数据库。

每次有效加载后，`[GroupRequests][handler]` 日志汇总已处理数量、缺少处理人 ID 数量、缺少昵称数量、已解析数量及资料查询是否成功。它不输出登录 token、原始响应、昵称或用户 ID，可区分历史字段缺失与资料查询失败。

若历史申请也必须显示处理人，服务端需核对原始审批/操作日志，按群 ID、申请人 ID、申请时间定位同一申请，将实际操作管理员写回 `handleUserID` 并保证 SDK 同步到更新记录。没有可追溯的历史记录时，不能从现任群主、管理员或邀请人推断处理人。
