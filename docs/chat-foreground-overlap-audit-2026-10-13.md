# 后台返回聊天的叠加场景检查（2026-10-13）

结论：页面层确实存在多处可以使恢复机会丢失的时序缺口，已修复并通过专项测试。但当前原生 SDK 二进制尚未包含仓库里的离线同步补丁；客户端有限补读不能保证修复从未成功写入 SDK 数据库的消息，因此仍不能判定此问题彻底消失。本轮未构建、安装手机包，未做 Android/iOS 真机后台验证。

## 本轮修复与覆盖

| 叠加条件 | 原问题 | 本轮处理 |
| --- | --- | --- |
| 摘要回调先到、消息稍后落库、没有逐条消息回调 | 同一缺失 ID 只查一次，成功读到旧页后不再恢复 | 100ms、1s、3s 有限核对；普通实时消息先到则取消多余读取 |
| 后台断网耗尽重试，再恢复网络或完成同步 | 已耗尽的预算没有重新开启 | 外部恢复事件开启新的有限预算，内部失败不自行续期 |
| 最新页读取在途，页面被覆盖，此时收到新消息，旧查询才结束 | 旧完成回调清掉新一轮待恢复标记 | 用覆盖期间的消息版本判断是否可以清除标记 |
| 已排队刷新开始后，又收到更晚的唤醒/持久化提示 | 仍复用已开始的排队查询，丢失再读一次的机会 | 排队任务开始时释放排队标记，允许合并一个后续刷新 |
| 覆盖页面期间重试暂停，或只有摘要回调没有消息回调 | 返回聊天时没有消息缓冲标记，恢复未触发 | 返回当前路由后检查错误及缺失摘要，不依赖单一消息缓冲标记 |
| 摘要恢复在途时清空记录，随后有新摘要 | 旧请求的运行标记阻止新恢复；迟到完成可能干扰新任务 | 清空推进恢复版本并释放旧运行归属，旧结果不可影响新窗口 |
| 日期定位失败，再切前后台、同步完成并收到最新摘要 | 通用最新刷新可能覆盖原失败动作 | 先恢复原日期目标/分页方向，保留历史窗口，不强制跳回最新 |
| 重试计时器触发时另一查询在途；旧窗口重试中发生新恢复 | 错误临时清空导致计时器退出；新恢复可能被旧请求吞掉 | 等查询结束重新检查；保留运行期间外部请求；新窗口替换旧计时器 |

另外覆盖：20 次连续切换前后台的请求合并、永久缺失摘要的请求上限、正常实时消息不多读、同步中延后刷新、历史窗口保持、输入草稿保留、清空/关闭/切账号后拒绝迟到结果。历史、缓存和已读模块回归覆盖去重、删除、私密消息、发送状态及视口授权。

## 仍可能发生的 SDK 级情况

1. **离线拉取或落库失败却报告同步结束。** 当前 Flutter 插件 Android 仍引用 `io.openim:core-sdk:3.8.3-patch12@aar`，iOS 仍引用 `OpenIMSDKCore 3.8.3-hotfix.12`。已对照匹配版本的原生 `msg_sync.go`：分批同步/派发的部分错误未传递到结束状态；部分同步序号在持久化确认前推进。页面重复读取本地历史不能补出未写入的数据。
2. **原生请求长期不返回。** Dart 等待超时不等于原生任务取消。保留最多两个真实在途历史读取是有意的限制；若它们永不释放，后续读取仍可能受阻。不能用不断新建请求或超时强制重登来绕过。
3. **只有最新摘要不足以证明历史完整。** 最新一条存在不能证明中间所有离线消息都补齐；最新摘要缺失的有限重试也不保证覆盖无限长的落库延迟。历史连续性、权限过滤与可靠序号提交仍由 SDK 负责。

受控修复位于 [native_sdk/README.md](../native_sdk/README.md) 和 `native_sdk/patches/0001-sdk-recovery.patch`，接入状态见 [SDK 修复记录](sdk-recovery-fixes-2026-10-13.md)。本轮没有改写原生 SDK 状态为“同步完成”，也没有更换原生依赖。

发布前还需接入并核对修复后的原生二进制，在 Android/iOS 真机验证：长时间后台及锁屏、后台断网后恢复同一种网络、Wi-Fi/移动网络切换、多群离线积压、同步中重复切前后台、清空/切账号与迟到回调，以及弱网/数据库失败后的补齐。验收应比较实际消息 ID 与服务端/发送端记录，不能只看同步完成标题。
