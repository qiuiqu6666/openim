# 模块目录与长期维护规范

本规范用于当前 OpenIM Flutter 项目的后续开发和整理。用户要求大小模块都有独立目录和文件，便于长期维护；因此，所有独立功能都必须有明确的归属目录，相关页面、状态、数据访问和组件应集中维护，一个实现文件承担一个明确职责。

本规范与根目录 [AGENTS.md](../AGENTS.md) 一起执行，保留现有 Flutter、GetX、OpenIM SDK、公共组件和路由体系。新功能立即遵守；现有代码按功能逐步迁移。下文的目标目录是整理标准，不表示现有文件已经全部迁移。

## 模块与子模块归属

一个独立用户功能或可单独维护的业务能力就是一个模块。大模块下的独立功能继续建立子目录；小模块同样有自己的目录和实现文件。简单功能可以只有一个实现文件，需要页面、控制器、仓储等职责时再添加对应文件和层级。

新增功能前必须先确认：所属模块、复用的公共能力、对外入口、状态所有者和测试位置。修复现有功能时，沿用已存在的归属目录，避免同时出现两套实现。

| 功能归属 | 目标目录 | 管理范围 |
| --- | --- | --- |
| 聊天 | lib/pages/chat/ | 聊天入口及历史、输入、回执、语音、媒体、表情和群设置子模块 |
| 联系人 | lib/pages/contacts/ | 好友、群列表、申请、资料、共同群和选择器等现有子模块 |
| 会话列表 | lib/pages/conversation/ | 列表、文件夹、置顶、免打扰及会话列表状态 |
| 收藏 | lib/pages/favorites/ | 收藏页面、详情、编辑、标签、数据访问及发送编排；聊天和我的页面调用其入口 |
| 朋友圈 | lib/pages/moments/ | 动态流、详情、发布、通知、权限、草稿及数据访问 |
| 资金 | lib/pages/fund/ | 红包、转账、详情、接收人选择及业务数据；聊天卡片属于聊天展示适配 |
| 我的与设置 | lib/pages/mine/ | 个人入口；settings 下按账号安全、隐私、通知、外观、存储、反馈、关于等再分目录 |
| 共享消息能力 | lib/services/messaging/ | 多个业务使用的发送契约、发送传输、历史缓存等，保持与具体业务页面独立 |
| 共享账号验证 | lib/services/account_verification/ | 登录、注册、找回密码和账号设置共用的验证码请求与验证能力 |
| 共享平台能力 | lib/services/platform/ | 关于、分享、升级等共用的平台配置访问 |
| 公共界面组件 | lib/widgets/ 或 openim_common/lib/src/widgets/ | 已被多个功能使用、接口不依赖具体页面的组件；按组件或组件族建立子目录 |

业务专用 API、模型、仓储和本地状态放回所属业务模块。只有调用方确实跨业务，且接口不依赖某个业务页面时，才归入共享目录。

openim_common 中被公共聊天组件使用的资金消息协议模型、语音展示状态等继续保持公共归属。公共包不得为了取业务模型而反向依赖应用页面。

## 文件职责与命名

1. 文件和目录使用 snake_case，不包含空格。保留现有 `_view.dart`、`_logic.dart`、`_binding.dart` 命名习惯；采用 `_page.dart` 的模块保持一致。
2. 一个实现文件只有一个主要职责。独立页面、弹窗、业务组件、控制器、仓储、API、模型、持久化服务分别放在可定位的文件中。
3. 大模块的主控制器负责协调和生命周期，具体历史、输入、语音、上传、交易等流程由子模块负责。抽取后明确由谁创建、取消、释放，不重复订阅 SDK。
4. 小功能可以在自己的目录中保持紧凑实现。Widget 与其 State 可以同文件；仅为该实现服务的少量私有辅助方法可以同文件。
5. 独立功能的新增实现必须进入对应子目录；不要继续追加到已有的大页面或大控制器。`widgets.dart`、`utils.dart` 等入口如需保留，应逐步承担导出或兼容职责。
6. 手写实现文件超过 500 行时检查是否包含可独立职责；超过 800 行时，新增功能前应完成职责拆分，或在模块说明中记录保留原因和后续拆分边界。生成文件、语言资源、合法文档正文按内容类型单独管理，不做机械拆行。
7. 修复现有超长文件中的紧急或局部问题可以保持改动范围；新增独立职责仍须拆出。不得为了满足行数阈值破坏私密消息、支付、草稿、未读数或 SDK 生命周期。

拆分必须实际明确状态和依赖的所有权。把同一个巨型控制器切成多个 part 文件，或用大量 extension 继续共享全部私有状态，不算完成模块职责拆分。

## 模块依赖与公共入口

页面负责显示和用户交互，控制器或流程协调器负责状态及异步任务，仓储和服务负责数据访问。数据层不得依赖页面 Widget 或从另一个页面文件取模型。

跨模块调用使用明确的入口、接口、回调或现有导航能力。需要共用的契约放在中性的共享目录，业务模块保留自己的适配器。两个模块不得新增相互导入的循环；模块内部循环同样应在拆分时消除。

公共能力不引用业务模块内部实现。`openim_common` 和 `openim_live` 保持各自包边界，沿用现有桥接接口。业务代码可以调用现有 SDK；本次目录规范不要求重写 SDK 层、数据库层或状态管理框架。

现有代码有下列迁移约束，需要在处理相关模块时一起核对：

- chat_message_sender 与 favorite_send_coordinator 相互导入。整理收藏发送模块时，先明确共享发送契约与收藏适配边界，再移动文件。
- favorite_runtime 参与账号退出清理；moments_repository 订阅 IM、好友及退出事件。移动目录时保留事件和清理链路。
- 收藏选择器直接复用 favorites_page 中的列表和状态格式化函数。先将业务组件独立，调用方再改为引用该组件。
- 登录、注册、找回密码引用设置 widgets 中的账号验证请求。整理时将共享验证能力独立，保留各入口的错误处理和验证码状态。
- 聊天背景服务有聊天、设置、资料等调用方。明确共享持久化归属，设置页面保留在外观子模块。

纯导出文件可集中提供模块入口，不应在导入时启动网络请求、注册监听或创建全局状态。

## 测试与模块说明

新建测试按源码功能目录对应组织。跨模块生命周期和业务流程测试放在独立 integration 目录，测试假实现也有明确模块归属。

```text
test/
  pages/
    chat/
      history/chat_history_loader_test.dart
      voice/voice_transcription_controller_test.dart
    favorites/
    fund/
    mine/settings/feedback/
  services/
    messaging/
    account_verification/
  integration/
    chat/chat_entry_performance_test.dart
    global_performance_regression_test.dart
  support/
    favorites/favorite_test_fakes.dart
```

纯公共包测试可以留在该包的 test 目录。实际依赖应用、资源、路由或 GetX 注册的公共组件测试继续在应用测试环境运行，不能仅为目录整齐改变测试环境。移动测试后检查资源路径和运行入口。

复杂模块应有简短 README，说明职责与子目录、公开入口、真实数据源、状态及资源所有者、测试位置和验证方式。小模块可在父模块 README 中登记。目录整理涉及的遗留异常和兼容入口也应注明。

## 现有代码整理顺序

聊天已执行首轮按功能拆分：历史、回执、输入、消息发送与操作、媒体、语音、表情、收藏适配、资金卡片、群状态、导航、通话和外观分别归属独立目录，主入口保留协调及兼容接口。实际入口和生命周期说明见 [聊天模块维护入口](../lib/pages/chat/README.md)。收藏主页面与共享服务、现有群设置细分页面及公共工具的进一步整理仍按下表逐项推进。

| 顺序 | 整理范围 | 完成标准 |
| --- | --- | --- |
| 1 | 已经独立的聊天历史、回执、媒体、语音文件；收藏公共列表与弹窗 | 文件进入明确子目录，调用方不再引用包含无关页面的巨型文件 |
| 2 | 收藏、朋友圈、资金的页面与数据服务 | 模块内能找到完整业务链路，跨模块只使用公开入口，保留账号退出与请求幂等处理 |
| 3 | 设置中的反馈、存储、二维码、外观、账号安全等 | 每个独立功能有自己的目录和实现，共享组件留在明确公共目录 |
| 4 | 聊天主控制器与公共 API、工具类的职责拆分 | 主入口承担协调职责，具体流程具有可单独验证的状态和生命周期边界 |
| 5 | 现有根级测试、命名和兼容导出 | 测试与模块对应，过渡兼容入口有明确用途且不保留重复实现 |

每次只迁移一个有明确边界的功能，先查全部调用方，再同步改引用、导出、路由、绑定和测试。路径整理与业务修复分别说明，保留原有行为；需要行为变更时单独解释和验证。

每次迁移完成应确认：相关测试可被发现并通过，修改范围 analyze 无新增错误或警告，跨模块无新增循环依赖，原有草稿、滚动、未读数、私密消息、支付恢复和退出清理链路正常。触及应用导入、路由或原生资源时补构建验证。

## 执行与检查

开发和审查时必须同时检查功能正确性与目录归属：新功能是否有独立目录、文件是否单一职责、业务专用服务是否归回模块、共享组件是否重复、调用边界是否清楚、测试是否对应。

目前这些模块边界由开发规则与审查执行。Flutter lints 尚未提供本项目的目录和依赖约束检查，不能将本规范描述为已经自动执行的检查。后续如增加自动检查，应先建立现有代码的迁移清单，再逐步对新增代码收紧约束。
