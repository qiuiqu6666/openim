# 朋友圈完整产品与前后端设计方案

版本：v1.3  
日期：2026-10-04（Asia/Taipei）  
适用项目：OpenIM Flutter 客户端，参考 99chat 的产品交互  
文档状态：完整设计基线；用户已提供当前后端契约，客户端据此适配；真实部署与多设备联调待完成

## 1. 文档用途与决策状态

本文统一朋友圈的产品行为、权限规则、前后端职责、数据模型、接口、状态流转、异常恢复与上线验收。开发和测试应以同一套规则执行，不能由各个页面分别解释。

**当前接入以 [已实现后端契约](moments-backend-contract.md) 为准。** 本文保留完整设计与后续阶段规划，不能把其中的建议接口都视为当前已上线。当前阶段只有图文；视频与举报关闭；能力以 `supportsMoments` 为准，分页使用 `limit`。客户端实际适配、字段大小写和仍待确认的成功响应结构见 [客户端接入说明](moments-client-integration.md)。

### 1.1 已确认的要求

1. 实现朋友圈功能，由本方案统筹前后端。
2. 先确定完整方案，再确定目标后端。
3. 点赞和评论中，非好友产生的互动不显示。
4. 本文按当前查看者的好友关系解释第 3 条：作者也没有查看非好友互动的例外；接口、计数、通知和缓存均执行一致规则。
5. 主入口使用现有“我的 → 社区广场”，进入后页面命名为“朋友圈”；后端由用户依据本文实现，客户端先实现页面与接口适配。
6. 用户已提供后端实现说明：使用当前 `chatToken`，OpenIM 业务通知 `key=moments`，非好友互动在服务端按查看者过滤；当前不开放视频、举报。
7. 两项隐私设置的 PUT/DELETE 已实现，但 `GET /moments/settings` 不返回名单。客户端使用本机已确认操作记录呈现选择，空记录显示“未选取”并允许添加/取消；不将缺少名单字段解释为功能不可用。后端继续负责实际权限和动态流过滤。

### 1.2 方案默认值

除上述要求外，本文列出的首期范围、双向好友判定、SELF 可见范围、历史范围、上传限制、删除规则等，属于建议采用的设计默认值。后续如调整，须同步修改接口契约、权限矩阵和测试。

第一版按好友朋友圈设计。前端沿用现有 Flutter / GetX / Dio / OpenIM SDK，业务数据接入最终选定的业务后端。先做独立业务模块，扩容时再依据实测拆分服务。

### 2.2 99chat 参考实现

参考客户端已有动态流、个人相册、发布、详情、通知、隐私设置、缓存和实时刷新；参考后端已有 /moments 模块。但其 Bearer JWT、业务用户表、双向好友库、响应包和 TCP 通道不等同于当前 OpenIM 项目。

可参考页面结构、操作路径和功能模型。身份、好友权威来源、网络适配、媒体授权和通知通道必须重新接入当前系统。

已核对的参考实现存在以下缺口，迁移时必须修正：

- 权限失败也可能回退展示旧缓存。
- 一次发布超时后再调用，会生成新的幂等键。
- Feed、详情和通知的权限过滤不完全一致。
- 选人名单可能返回给普通浏览者。
- 点赞评论没有落实本文要求的非好友过滤。
- 游标时间精度、过滤分页和上传恢复存在边界问题。

## 3. 产品范围与页面清单

### 3.1 第一阶段：完整图文闭环

| 页面 | 入口与职责 | 必须具备的状态 |
| --- | --- | --- |
| 好友动态流 | 我的 → 社区广场 → 朋友圈 | 首次加载、刷新、更多、空、错误、失效 |
| 我的朋友圈 | 本人资料页或动态流本人头像 | 封面、历史动态、发布、删除、修改范围 |
| 好友朋友圈 | 好友资料页或作者头像 | 历史范围提示、无权限、空、加载失败 |
| 发布页 | 朋友圈发布按钮 | 编辑、草稿、准备、上传、提交、结果待确认 |
| 动态详情 | 点动态或合法通知 | 内容、可见互动、互动分页、不可用 |
| 互动消息 | 朋友圈消息入口 | 可见通知、未读、分页、已读反馈 |
| 隐私设置 | 现有朋友圈权限页 | 历史范围、禁止查看、隐藏作者、保存失败 |
| 举报入口 | 动态或评论菜单 | 选择原因、提交、处理中、结果 |

动态流显示作者、正文、媒体、时间和当前查看者可见的互动。个人相册可按日期组织；两者共用动态实体和权限结果。

本人资料页可进入“我的朋友圈”，好友资料页可进入好友朋友圈。主入口保留“社区广场”命名，进入后显示“朋友圈”，沿用现有导航结构。

### 3.2 第二阶段：短视频与增强

开放“文字 + 一个短视频”，完成真实视频封面、时长、尺寸、转码、播放和失败恢复。图片与视频不混排；多视频不在本方案首期范围内。

视频启用前必须确定时长、大小、格式和清晰度限制，并同时落实客户端与服务端校验。具体参数由存储与处理能力实测确定。

### 3.3 发布默认限制

| 内容 | 设计默认值 |
| --- | --- |
| 正文 | 去除首尾空白后最多 2000 个 Unicode 码点 |
| 评论 | 去除首尾空白后 1～500 个 Unicode 码点 |
| 图片 | 最多 9 张，顺序可调整；单张上传文件建议不超过 10 MiB |
| 图片格式 | JPEG、PNG、WebP；服务端校验实际文件内容 |
| 空动态 | 正文与媒体不能同时为空 |
| 视频 | 第二阶段一个视频，具体大小、时长由选定后端确定 |
| 发布范围 | 默认 FRIENDS |
| 正文及媒体编辑 | 首期发布后通过删除重发处理 |
| 范围编辑 | 支持修改单条可见范围并重新授权 |

前端必须保留原始选择文件或受管理的本地副本，不能仅依赖选择器临时路径。不得静默丢弃上传失败的附件后继续发布。

## 4. 身份、鉴权与好友权威来源

### 4.1 身份边界

- 客户端对外作者、好友和互动用户标识沿用当前 IM userID。
- 业务内部 ID 与 IM userID 不假定相同，由服务端使用已有映射关联。
- 手机号、账号名、昵称不作为朋友圈关系主键。
- 接当前业务后端时使用 chatToken；imToken 用于 OpenIM SDK。
- 服务端验证 token、会话状态和账户状态，从认证主体决定操作者。
- 发布、点赞、评论接口不信任客户端提交的作者 ID。
- token 不写入草稿、发布任务、资源 URL、普通日志或通知内容。

如最终后端使用不同认证体系，增加受验证的身份桥接或会话交换；不能把 chatToken 直接当作 99chat 的 Bearer JWT。

### 4.2 好友判定

本文默认“当前好友”表示服务端当前有效的双向好友关系。客户端好友列表只辅助展示和选择，不能作为授权依据。

最终后端必须指定唯一的好友权威来源：若现有业务后端拥有完整好友链，使用其权威数据；若由 OpenIM 管理，朋友圈通过适配器读取或维护其查询投影。

查询投影只用于优化，不成为第二套独立好友真相。投影需要关系版本、更新事件、失败重试、定期校准和新鲜度检查。失去新鲜度或无法确认关系时，回查权威源；回查失败不继续按旧关系放行。

OpenIM 与业务数据库跨服务，不能宣称一个本地事务就实现两套系统同时撤权。后端选定时必须确定撤权完成时点、关系变更确认路径和同步延迟目标。

## 5. 动态可见权限

### 5.1 单条可见范围

| 范围 | 含义 | 名单要求 |
| --- | --- | --- |
| SELF | 仅自己 | 不接受选人名单 |
| FRIENDS | 所有当前好友 | 不接受选人名单 |
| PARTIAL | 部分当前好友 | 名单非空；发布或修改时校验当前好友 |
| EXCLUDE | 当前好友中排除指定用户 | 可为空；名单不授予任何额外权限 |

统一使用 audienceUserIds 字段。它在 PARTIAL 中表示允许名单，在 EXCLUDE 中表示排除名单。选定后端若保留旧 visibleUserIds 字段，须由 API 层显式映射，不能让客户端同时混用两种语义。

名单在读取时仍与当前好友关系叠加。曾经在 PARTIAL 名单内的用户，删除好友后不能继续访问；重新加好友后，如果 ID 仍在名单内，可按当前规则恢复访问。

名单只返回作者。其他查看者的 DTO 不包含 audienceUserIds，也不返回隐藏名单的长度。

### 5.2 用户级设置

| 设置 | 生效规则 |
| --- | --- |
| visibleRangeDays | 默认 0 表示全部；支持 3、90、180、365 天 |
| blockedViewer | 不让指定用户访问我的全部朋友圈内容 |
| hiddenAuthor | 只从我的好友动态流过滤指定作者 |
| IM 黑名单 | 任一方向有效拉黑时，阻断双方朋友圈访问和新增互动 |

时间范围按服务端 UTC 时间计算滚动 N × 24 小时。本人查看自己的正常动态不受时间范围限制。修改设置作用于历史内容；单条名单不能覆盖全局拒绝条件。

“不看他”不等于“不让他看”，也不等于 IM 拉黑。这三种关系必须分开保存、展示和解释。

### 5.3 统一判定顺序

先确认内容状态，再确认身份和关系，最后计算时间与单条范围。

```text
正常阅读：
  动态必须处于 PUBLISHED 且未删除
  若查看者是作者：允许读取自己的动态
  否则同时满足：
    作者与查看者是当前双向好友
    双方无有效 IM 拉黑关系
    查看者不在作者 blockedViewer 中
    动态在作者 visibleRangeDays 范围内
    单条 visibility 允许查看者

Feed 额外规则：
  排除当前查看者 hiddenAuthor 中的作者
  查看者自己的动态不受该偏好过滤
```

作者查看审核中、驳回或下架内容，使用本人管理视图，展示状态及允许返回的原因；它们不进入普通动态流。删除状态不通过正常阅读接口恢复。

### 5.4 必须覆盖的入口

统一权限策略覆盖动态流、个人相册、详情、点赞列表、评论列表、通知预览、媒体与缩略图、新增互动、回复目标校验及实时事件的受众判断。

接口返回 canLike、canComment、canDelete、canEditVisibility 等当前能力，服务端在执行操作时仍重新校验。客户端显示按钮不能替代服务端授权。

## 6. 点赞、评论与回复的可见性

### 6.1 用户确认的核心规则

**非好友产生的点赞和评论不显示。判断依据是当前查看者的当前好友关系；动态作者也执行相同规则。**

```text
互动用户可见(viewer, actor) =
  actor 是 viewer 本人
  OR actor 是 viewer 当前好友且双方未有效拉黑

点赞可见 =
  动态可见 AND 互动用户可见

普通评论可见 =
  动态可见 AND 评论未删除 AND 互动用户可见

回复可见 =
  当前回复满足普通评论可见条件
  AND 被回复用户是 viewer 本人或 viewer 当前好友
  AND 根评论与实际回复目标的授权条件成立
  AND 目标未删除时可正常读取；目标已删除时仅允许无正文、无姓名头像占位
```

本人互动可见只豁免操作者的好友检查，不能绕过动态权限、回复目标权限、删除或下架状态。本人回复了一个现在已非好友的人时，也按回复规则整条隐藏。

### 6.2 过滤范围

- 动态流和相册中的点赞、评论预览。
- 动态详情、点赞分页和评论分页。
- 点赞、评论等写接口返回的当前动态结果。
- 互动通知列表、未读数、推送和实时摘要。
- 服务端缓存、客户端缓存和导出的普通用户数据。

服务端先过滤再返回，不把完整互动列表交给客户端隐藏。不可见互动的用户 ID、头像、昵称、原文、回复目标和摘要都不返回。

### 6.3 数量与分页

likeCount 和 commentCount 都表示“当前查看者可见数”。可见数可能因查看者不同而不同，作者没有全量计数例外。

评论预览长度不是评论总数；分页、预览、数量使用同一套过滤规则。hasMore 只反映后面是否还有该查看者可见的互动。

服务端内部可以保存运营统计，但不能将未过滤的统计放入普通用户 DTO、角标或分页字段。

### 6.4 回复与删除

回复采用扁平展示，服务端从 replyToCommentId 推导目标用户；不信任客户端指定的 replyToUser。回复目标必须属于同一动态且操作者有权查看。

第一版回复层级固定为一层：普通评论可直接回复；对回复条目继续回复时，服务端保存原根评论和实际被回复条目，界面仍展示在同一层。根评论和实际目标都需要通过权限检查。

回复目标被删除时可保留其无正文占位关系，其他合规回复继续存在，展示“已删除评论”。服务端仍校验根评论与实际目标原操作者的当前好友及拉黑权限。只对当前查看者已获授权的删除目标返回 `replyTargetDeleted: true` 和最小 `replyToUser: {"userId":"已授权的 IM 用户 ID","nickname":"","avatarUrl":"","remark":""}`，用于客户端再次校验好友关系；不返回目标正文、原姓名、头像或备注，界面也不展示该用户 ID。这个 ID 必须本来属于当前查看者可见的本人或好友，不能泄漏非好友身份。

`replyTargetDeleted` 仅描述目标正文状态，不能作为权限证明。客户端目标身份缺失、好友关系无法确认或目标已非好友时，保守隐藏整条回复，并不展示未经确认的总数。模型会剥离删除目标的姓名、头像和备注；界面使用 `replyTargetLabel` 的“已删除评论”，不要使用匿名目标 `displayName` 的 ID 回退。目标因非好友或其他权限原因不可见时，服务端直接过滤相关回复，不返回目标 ID 或身份残片；通知中的同一引用也执行相同契约。

### 6.5 操作管理与内容读取分开

用户可删除自己的评论、取消自己的点赞；作者可删除自己的动态，并按管理权限删除该动态下的评论。管理接口不返回不可见正文或父动态内容，第一版界面不展示隐藏评论。

失去动态阅读权限后，用户仍可通过本人互动清理能力处理自己的旧记录。管理权限不会恢复阅读权限。

### 6.6 关系变化示例

假设 A 发布动态，B 评论，C 与 A、B 都是当前好友：

1. A 与 B 仍是好友时，A 可以看到 B 的评论。
2. A 删除 B 后，A 看不到 B 的评论，A 的可见评论数随之减少。
3. C 仍能访问 A 的动态，且 C 与 B 仍是好友，因此 C 可以继续看到 B 的既有评论。
4. B 无权继续读取 A 的动态，但可以清理自己原来的评论。
5. 重新加好友后，未删除的历史互动可以按当前规则重新出现；不重置已读状态，也不补发历史互动通知。

这说明关系变化应重新计算展示结果，不应全局删除历史互动。

## 7. 用户操作与发布状态

### 7.1 浏览流程

进入朋友圈 → 确认当前会话 → 读取合法缓存或显示加载态 → 获取首屏 → 展示内容与可见互动 → 游标加载更多。

返回页面时保留列表和滚动位置；仅刷新失效或过期数据。网络失败与真实空列表使用不同状态。

### 7.2 草稿与发布任务分离

| 对象 | 保存内容 | 可编辑性 |
| --- | --- | --- |
| Draft | 文字、范围、名单、本地媒体及顺序、修改时间 | 可编辑 |
| PublishJob | 固定 clientRequestID、冻结内容、媒体任务、mediaId、请求指纹、执行状态 | 提交期间冻结 |
| MediaTask | 本地副本、clientMediaId、上传会话、进度、校验信息、服务端状态 | 支持单项恢复 |

点击发布时先持久化 PublishJob，再执行网络请求。修改被冻结的内容需要先确认原任务未发布，再生成新的任务 ID，不能用旧 ID 提交不同内容。

### 7.3 客户端发布状态

| 状态 | 含义 | 下一步 |
| --- | --- | --- |
| DRAFT | 编辑中 | 保存、放弃或创建任务 |
| PREPARING | 压缩、检查文件和准备上传 | 上传或提示准备失败 |
| UPLOADING | 上传媒体 | 单项进度、重试、提交前取消 |
| READY_TO_COMMIT | 全部媒体已 READY | 提交冻结内容 |
| SUBMITTING | 发布请求已发送 | 等待结果 |
| SUBMIT_UNKNOWN | 超时、断网或进程结束，结果不确定 | 查询结果，同键重试 |
| SUBMIT_FAILED | 服务端明确拒绝 | 修正内容或放弃任务 |
| AWAITING_AUTH | 会话失效 | 同一账号恢复登录后继续 |
| COMMITTED | 服务端确认动态事务已保存 | 更新实体并清理已完成任务 |
| CANCELLED | 提交前成功停止任务 | 保留或清理草稿 |

COMMITTED 只表示发布事务已保存，动态是否对好友可见由服务端资源状态决定。正在审核时，任务已完成，动态处于 PENDING_REVIEW；界面显示“已提交，等待审核”，不能显示成已对好友发布。

### 7.4 结果不确定的恢复

```text
请求超时或应用结束
  → 保留固定 clientRequestID 和内容指纹
  → 查询本人发布结果
  → SUCCEEDED：合并真实 momentId 和当前资源状态
  → REJECTED：展示可修正原因
  → PROCESSING：继续有界查询，禁止换键重复发布
  → NOT_FOUND：只用原 ID 和相同内容重试
```

NOT_FOUND 不代表之前的请求一定不会随后到达，因此同键重试始终由服务端幂等约束保护。客户端取消等待不等于服务端取消创建。已经发布后的撤回通过独立删除流程完成。

### 7.5 点赞和评论

点赞使用明确的目标状态；同一动态的客户端操作串行或合并最后意图，防止请求乱序。乐观展示失败时只回滚对应操作，不能覆盖后来收到的新版本。

评论也保存稳定请求 ID。服务端确认后用真实 commentId 替换待发送条目；结果未知时核对原请求，不换键重发。提交回复前后均验证目标权限。

## 8. 前端分层、缓存与生命周期

### 8.1 职责划分

| 层 | 职责 |
| --- | --- |
| 页面 Widget | 展示状态、收集操作、使用统一主题和组件 |
| GetX Controller | 输入、页面加载态、滚动、弹窗和页面生命周期 |
| MomentsRepository | 动态实体、各查询 ID 顺序、分页、互动状态和权限失效 |
| MomentsSettingsRepository | 设置读取、单项修改、版本冲突和账号隔离 |
| MediaRepository / PublishWorker | 持久任务、上传、取消、恢复和结果核对 |
| MomentsApi | 鉴权、追踪 ID、DTO、响应包和结构化错误 |
| SDK 适配器 | 好友选择、关系变化和自定义业务事件订阅 |
| AccountScopedCache | 按账号和服务环境保存受限缓存与草稿 |

页面不直接取 token、请求 API、决定后台权限或覆盖全局 SDK listener。

### 8.2 共享实体

账户级 Repository 维护 postsById、commentsById、用户资料及每个查询的 ID 顺序。Feed、我的相册、好友相册和详情共用实体，避免点赞、删除或修改范围后页面之间不一致。

互动投影与数量是查看者相关数据，不能作为全用户共享的动态属性缓存。服务端资源 version 与 viewerContextVersion 分开处理；关系变化即使未修改动态，也必须使当前查看者的互动结果失效。

删除保留 tombstone，撤权保留失效标记；迟到响应不能将不可用内容重新显示。

### 8.3 会话与请求隔离

SessionScope = 服务环境 + IM userID + 登录代数。退出、换账号或换服务器递增代数，取消旧请求并清空当前私密内存状态。

异步结果只有在 scope、查询代数和权限上下文仍匹配时才能回写。鉴权恢复后只能由同一环境、同一账号继续原任务。

### 8.4 列表状态

区分首次加载、已有内容、刷新、加载更多、真实空列表、首次错误、离线旧快照和权限失效。

刷新开始后丢弃旧加载更多响应。同一查询只允许一个加载更多请求；按 ID 去重；游标未前进时停止自动加载并报错。筛选条件变化重新创建查询。

### 8.5 缓存与撤权

- 缓存至少包含服务环境、账号、查询范围和授权有效期。
- 遇到权限拒绝、删除、下架，停止展示并清理对应内容和媒体引用。
- 权限错误不能降级为“从缓存恢复旧内容”。
- 恢复前台先更新会话和权限，再恢复动态展示。
- 私密正文和媒体不无限期离线展示；过期且无法确认权限时显示联网查看状态。
- 媒体缓存按账号、mediaId 和媒体版本隔离，维护对象到本地文件的引用关系。
- 退出登录清理私密展示缓存；草稿按账号隔离保存，账户注销时清理。

### 8.6 生命周期

| 时点 | 行为 |
| --- | --- |
| init | 订阅 Repository、恢复状态、决定是否请求 |
| 页面覆盖 | 保留滚动和草稿，暂停视频及高成本预取 |
| 页面恢复 | 刷新失效内容，恢复可用状态 |
| 应用后台 | 持久化任务，暂停非必要刷新和播放 |
| 应用前台 | 确认会话、同步权限、核对未知提交、同步通知 |
| dispose / onClose | 取消页面订阅、释放控制器，禁止写已销毁页面 |
| 账号变化 | 停止旧任务、解绑订阅、清理当前账号展示状态 |

上传任务由账户级工作器管理，不因编辑页返回而丢失。系统终止后保证可恢复记录，不承诺所有平台都能持续后台上传。

### 8.7 UI 与平台验收

复用 AppTokens、AvatarView、TitleBar、ThemeAwarePage、SettingsScaffold、已有媒体浏览器和选择组件。多图编辑与发布任务没有等价组件时才新增。

检查亮暗主题的正常、选中、禁用、加载、空、错误状态；检查 Android / iOS 的安全区域、键盘、返回、相册权限、视频播放和后台恢复。长列表使用懒构建，动态高度不强行设置固定 itemExtent。

## 9. 后端数据模型与一致性

### 9.1 逻辑表

具体物理表名和字段类型沿用最终后端规范，以下为逻辑模型。

| 表 | 关键字段与约束 |
| --- | --- |
| moment | id、authorId、clientRequestID、requestHash、text、status、visibility、createdAt、publishedAt、version、deletedAt |
| moment_audience | momentId、userId；组合唯一 |
| moment_media | id、ownerId、momentId、clientMediaId、objectKey、type、status、尺寸、大小、摘要、顺序、createdAt、expiresAt |
| moment_like | momentId、userId、createdAt；组合唯一 |
| moment_comment | id、momentId、authorId、clientRequestID、requestHash、text、rootCommentId、replyToCommentId、replyToUserId、createdAt、version、deletedAt |
| moment_settings | userId、coverMediaId、visibleRangeDays、version |
| moment_blocked_viewer | ownerId、viewerId；组合唯一 |
| moment_hidden_author | viewerId、authorId；组合唯一 |
| moment_notification | id、recipientId、actorId、momentId、commentId、type、seq、readAt、revokedAt |
| moment_notification_state | recipientId、lastSeq、readThroughSeq、version；按收件人唯一 |
| moment_idempotency | principalId、operation、key、requestHash、status、resourceId、result；组合唯一 |
| moment_outbox | eventId、aggregateId、aggregateVersion、action、status、attempts、nextRetryAt |
| moment_report | reporterId、对象类型与 ID、原因、证据引用、处理状态 |
| moment_audit | 操作者、管理动作、对象、原因、时间、追踪 ID |

好友关系和黑名单来自既有权威链；如需查询投影，另外保存 sourceVersion、syncedAt 和校准状态，不复制出另一套业务规则。

### 9.2 约束与索引

- 点赞唯一键：momentId + userId。
- 发布和评论幂等唯一键：principalId + operation + key。
- 动态与评论各自保留 authorId + clientRequestID 唯一约束及请求指纹，幂等记录归档后仍防止迟到重试重复创建；删除保留请求标识墓碑。
- 媒体去重键：ownerId + clientMediaId，配合文件摘要校验。
- 通知唯一键：recipientId + 业务事件键，避免事件重试生成重复通知。
- 通知序号唯一键：recipientId + seq；序号按收件人串行分配并与通知写入同一事务提交。
- 动态查询索引覆盖 authorId、status、publishedAt、id。
- 评论查询索引覆盖 momentId、deletedAt、createdAt、id。
- 通知索引覆盖 recipientId、seq，以及未读查询条件。
- outbox 索引覆盖 status、nextRetryAt。

互动存储保留事实，不保存一个会直接泄漏的“所有人通用展示计数”。第一版可批量聚合可见数量，后续优化仍须保持查看者维度。

### 9.3 发布事务

认领幂等键并检查 requestHash → 校验本人 READY 媒体 → 创建动态 → 保存名单 → 原子绑定媒体 → 保存通知或业务事件 → 写 outbox → 保存成功结果 → 提交。

同键同内容返回同一资源；同键不同内容返回冲突。并发认领依赖唯一约束与事务处理，不使用“查询没有再插入”作为唯一保护。

幂等记录保存资源标识和执行事实，不长期重放包含正文、名单或互动用户资料的旧响应。幂等重放、发布结果查询和评论结果查询中的可读字段都按当前权限重新组装；不可读时只返回本人操作结果、资源标识与不可用状态。评论已经成功但目前不可见时，仍向本人确认成功并返回 commentId 供清理，不返回评论正文、目标身份或父动态内容。

媒体通过锁或条件更新防止被两个动态同时绑定。动态删除后，原发布幂等键仍不能再次创建内容；重放结果返回原资源标识和当前不可用状态，不返回已删除正文。

### 9.4 操作与撤权竞态

关系或 ACL 与动态写入同库时，授权检查与写入使用同一事务及锁或版本条件。跨服务好友源通过已定义的关系版本和新鲜度策略保证边界，不把一次远程检查描述为永久授权。

后端必须定义“撤权提交完成”的确认条件；满足该条件后，新读取、新互动和新的媒体授权应拒绝。已开始返回的数据和已下载内容不在远程收回能力内。

点赞、取消点赞、评论创建或删除、范围修改、审核状态变化及动态删除，实际产生变更时都在事务内推进对应动态的聚合 version，并写入携带该版本的 outbox。无变化的幂等重放不重复推进版本。关系或用户级隐私变化推进 viewerContextVersion；它不依赖某条动态被修改。

## 10. API 契约

### 10.1 通用约定

- 基础路径：/moments，均为业务后端接口。
- 接当前业务后端时，沿用 token: chatToken 和现有 errCode / errMsg / errDlt / data 响应包。
- 每次网络请求使用新的 operationID；同一次业务尝试的 clientRequestID / Idempotency-Key 保持不变，两者用途不同。
- 时间对外统一毫秒时间戳；游标保留数据库真实排序精度。
- 默认 pageSize=20，最大 50；所有列表返回 items、nextCursor、hasMore。
- 写接口返回针对当前操作者过滤后的结果，不能返回全量互动。
- 数字错误码须在目标后端统一注册，本文使用语义名称说明处理规则，不预占线上错误码。
- 传入客户端版本和能力信息，用于范围、视频和协议能力协商。

成功响应形态：

```json
{
  "errCode": 0,
  "errMsg": "",
  "errDlt": "",
  "data": {
    "items": [],
    "nextCursor": null,
    "hasMore": false,
    "viewerContextVersion": "opaque-context-version"
  }
}
```

viewerContextVersion 是当前账号的关系与隐私上下文版本标识，不暴露具体好友名单。它与资源 version 共同用于响应回写及缓存失效。

当前 Flutter 数据层已按上述路径实现协议 v1 适配，具体请求头、响应信封及字段以 [客户端接入契约](moments-client-integration.md) 为准；这仅说明客户端实现情况，不证明目标后端已提供或部署这些接口。能力响应必须显式返回整数 `protocolVersion: 1`，缺失或不受支持的版本按未开放处理。

sync 请求只处理数量受限的客户端已缓存 ID，例如每次不超过 50 个；响应仅返回合法更新或 unavailable 标记，不返回被撤权正文。普通用户管理接口与后台管理接口分别鉴权。

### 10.3 创建动态请求

```json
{
  "clientRequestID": "固定的发布任务 UUID",
  "text": "今天的记录",
  "mediaIds": ["media_001", "media_002"],
  "visibility": "PARTIAL",
  "audienceUserIds": ["im_user_002", "im_user_003"]
}
```

header 中 Idempotency-Key 与 body 的 clientRequestID 使用同一任务标识；同时存在时必须一致。服务端保存规范化内容指纹，指纹包含媒体 ID、顺序和可见范围，不包含每次变化的 operationID。

### 10.5 设置更新与冲突

```json
{
  "expectedVersion": 4,
  "visibleRangeDays": 90
}
```

清除封面使用明确的 coverMediaId: null；字段缺省表示不修改。增加或移除某个屏蔽关系使用单项接口；如未来支持整表替换，必须携带版本防止多设备覆盖。

服务端先确认设置写入成功并推进权限版本，再返回；客户端随后更新展示。保存失败保留原值并显示错误，不能显示已保存。

## 11. 媒体存储、处理与访问

### 11.1 媒体状态

| 状态 | 含义 |
| --- | --- |
| UPLOADING | 接收文件或分片 |
| PROCESSING | 校验、解码、生成缩略图或转码 |
| READY | 通过检查，可绑定动态 |
| FAILED | 上传或处理失败，返回可重试原因 |
| EXPIRED | 未绑定且过期，不再可发布 |

上传完成后校验真实类型、大小、文件摘要和归属。图片限制解码尺寸，避免异常文件消耗；视频第二阶段提取真实封面、时长和尺寸并转码。

同一个 clientMediaId 对应相同文件时返回原上传结果，不重复创建；不同文件使用同 ID 返回冲突。首期可重试整个单文件上传，不宣称具备未实现的分片断点续传。

### 11.2 授权访问基线

私有桶保存原图、缩略图和视频。首期采用鉴权媒体代理：每次新读取、缩略图和视频 Range 请求先确认当前会话及动态权限；未发布媒体仅允许归属者预览。

返回给客户端的代理路径不包含 token，不暴露永久对象 URL。需要绕过原浏览器组件请求能力时，应扩展现有 MediaSource 的认证下载适配，保留已有浏览器交互。

共享 CDN 不缓存私密响应；服务端边缘缓存若启用，必须包含账户与授权上下文或逐请求鉴权，不能仅用 mediaId 作为公开缓存键。封面采用相册授权规则，头像沿用既有资料权限。

如后续改成短期签名 URL，需要单独定义有效期及撤权窗口。旧签名到期前仍可能有效，不能继续宣称所有新请求都即时撤权。

### 11.3 清理与回收

- 未绑定对象建议保留 24 小时作为恢复窗口，具体期限由存储容量确定并通过能力配置告知客户端。
- 清理前再次确认未绑定、非活跃上传或发布任务，避免与提交并发误删。
- 存储写入成功但数据库失败的孤儿对象可通过对象标签、上传记录或对账任务发现。
- 删除动态后按约定保留期异步回收媒体；保留举报证据的对象独立管理。
- 服务端回收、客户端缓存清理和系统相册文件是不同生命周期。

权限变更可阻止后续授权访问；已下载、已保存到相册或已在途返回的字节不能远程收回。

## 12. Feed、互动分页与性能

### 12.1 第一版查询方式

采用读取时聚合：查询本人及当前好友作者，叠加状态、历史范围、禁止查看、单条名单；Feed 再排除 hiddenAuthor。权限尽量在数据库查询中完成，然后限量返回。

第一版不要求预先向每个好友复制完整动态。好友资料、互动预览和数量批量获取，避免每条动态分别调用 SDK 或远程接口。

### 12.2 游标规则

动态按 publishedAt DESC、momentId DESC 排序，使用 keyset 游标。排序字段保持不可变；游标保留数据库真实精度，不能用显示层的毫秒值截断微秒排序值。

游标由服务端生成，绑定账号、查询范围、筛选条件及协议版本，并验证完整性。客户端只透传。需要固定首屏上界时使用服务端定义的水位；不承诺跨多次请求保持一个长期数据库事务快照。

关系或筛选上下文变化、游标过期时返回需要刷新，客户端重新获取首屏。新动态通过刷新首屏获得；已有条目按 ID 去重。

### 12.3 过滤后续传

不能因为当前扫描批次中大量条目不可见，就返回 hasMore=false。如果必须限制扫描工作量，返回准确扫描游标和继续扫描标志；客户端有界继续，不进行无限自动空页请求。

点赞和评论先按当前查看者过滤，再计算数量和分页。只剩不可见互动时 hasMore=false，不向用户泄漏隐藏条目规模。

### 12.4 优化顺序

先观察慢查询和实际规模，再增加查询缓存、关系投影、预聚合或 Feed 扇出。所有优化保持权限版本和查看者维度；Redis、独立消息队列或服务拆分依据实测引入。

## 13. 通知、未读与实时同步

### 13.1 接收人与可见规则

| 事件 | 候选接收人 |
| --- | --- |
| 点赞 | 动态作者 |
| 普通评论 | 动态作者 |
| 回复 | 动态作者与被回复者，去重 |
| 自己操作 | 不通知操作者本人 |

候选接收人还必须当前有权读取动态及该互动。作者不豁免非好友规则。历史互动后来变为不可见时，该通知项和未读数同步过滤。

取消点赞撤销该有效点赞的未读通知；重复点赞或事件重试不重复通知。评论删除、动态删除或下架使引用内容失效。非好友互动通知直接隐藏；其他失效内容可显示无正文、无身份、无媒体的“内容已不可用”记录，不计未读。

通知存引用，读取时重新授权。不能把旧正文、缩略图或用户名快照作为绕过当前权限的展示来源。

### 13.2 已读水位

通知列表返回服务端验证的 seenWatermark，绑定当前收件人及其本次已提交的截止序号。显示过的指定通知可按 ID 标记已读；用户明确操作“全部已读”时提交 readThroughSeq，服务端验证它不超过水位，并只作用于当前收件人且 seq 不大于该序号的记录。

同一收件人的 seq 分配与通知插入在一个事务中串行执行，例如锁定 moment_notification_state 后递增并插入，提交后才允许下一个序号事务继续。读取水位取已提交状态，不能提前暴露尚未提交的分配值。这样不会在用户读到 100 后，又迟到插入一个序号不大于 100 的未读通知。

“全部已读”持久化单调递增的 readThroughSeq；单条已读保存 readAt。有效已读为 readAt 非空或 seq 不大于持久水位，未读还须通过当前可见资格检查。后到的较小已读请求不降低水位，重复请求幂等。

```json
{
  "readThroughSeq": 100,
  "seenWatermark": "server-issued-watermark"
}
```

用户看到第 100 条后，新到第 101 条，标记到 100 不会把 101 一起读掉。进入通知页不直接把全部未读归零。后端校验收件人和水位归属，不能读取其他账号通知。

### 13.3 可靠事件

动态和互动事务中写 outbox；后台 worker 重试发送。事件包含 eventId、momentId、action、aggregateVersion、发生时间和必要的失效标识，不带正文、媒体地址或选人名单。

发送时重新检查受众；重复按 eventId 去重，乱序按版本处理。普通内容变更只向当前合法受众发送。撤权事件可以向曾获授权的设备发送不含内容的 invalidation，用于删除其已知缓存。

OpenIM 自定义业务事件或最终后端实时通道用于提示刷新，具体能力须与部署版本核对。断线后补拉通知，并批量校验已缓存内容；不能依赖每条在线推送都成功。

离线推送使用经过接收资格检查的通用提醒，不放私人正文和图片。点击后重新加载授权内容。低敏感系统提示与私密互动内容分别设计，避免通知栏长期保留已撤权信息。

## 14. 删除、审核、举报与账户生命周期

### 14.1 动态状态

| 状态 | 普通查看者 | 作者管理视图 |
| --- | --- | --- |
| PENDING_REVIEW | 不可见 | 显示等待审核 |
| PUBLISHED | 按权限可见 | 可管理 |
| REJECTED | 不可见 | 显示允许返回的原因 |
| HIDDEN | 不可见 | 显示下架状态和处理路径 |
| DELETED | 不可见 | 可查最小操作结果，不通过正常接口恢复正文 |

若首期没有自动审核，使用明确的人工举报处理路径；不将未执行检查描述为已完成审核。正式对外上线必须有举报、下架、禁发和审计能力。

### 14.2 删除规则

动态作者删除自己的动态，重复删除幂等；评论本人及有管理权的动态作者可删除评论。正常 API 对不可用资源不返回原文、互动或媒体。

删除操作同步更新资源版本、通知资格、缓存失效事件和回收计划。用户端首期不提供恢复入口。后台如允许恢复，重新执行审核及当前权限，并生成新版本，不能复活旧缓存。

### 14.3 举报与管理

举报记录对象、原因、提交人和服务端证据引用。管理操作支持动态或评论下架、账号禁发、处理状态和操作审计。

管理员读取证据使用独立管理权限和审计；它不属于普通作者查看全部互动的例外，也不能通过用户接口暴露。

发布、评论、上传和举报都有频率及配额限制，返回可理解的等待或限制信息。具体阈值在目标部署压测后配置，避免硬编码分散在页面。

### 14.4 账号注销与长期数据

账号注销后关闭发布和普通访问，按既有账户策略隐藏或删除其动态；用户资料引用使用明确的注销占位，不泄露已移除资料。

保存期限、举报证据期限、幂等记录期限和对象回收期限由业务及运维策略确定。幂等结果过期后仍须通过资源上的原请求标识防止迟到重试再次创建。

## 15. 错误、离线与恢复策略

| 语义错误 | 前端行为 | 数据处理 |
| --- | --- | --- |
| AUTH_REQUIRED | 恢复登录，任务进入 AWAITING_AUTH | 不交给其他账号继续 |
| MOMENT_UNAVAILABLE | 显示内容不可用 | 清理正文、互动与媒体引用 |
| PERMISSION_REVOKED | 停止展示并同步权限 | 禁止恢复旧缓存 |
| IDEMPOTENCY_CONFLICT | 提示请求内容冲突 | 核对原任务，不换键盲重发 |
| VERSION_CONFLICT | 拉取新版本后重做用户选择 | 不静默覆盖其他设备设置 |
| MEDIA_NOT_READY / MEDIA_EXPIRED | 等待处理或恢复上传 | 不静默减少附件 |
| RATE_LIMITED | 显示等待时间 | 有界重试 |
| CURSOR_EXPIRED / CONTEXT_CHANGED | 重新取首屏 | 丢弃旧游标和迟到响应 |
| 网络超时 | 读取保留受限合法状态；写入进入未知结果核对 | 不当作空列表或确定失败 |

对猜 ID 等读取请求，不暴露资源是否存在或内部数据库错误。恢复顺序为：当前身份 → 关系与权限 → 未知提交 → 通知 → 列表及媒体。

重试采用退避、次数上限和用户可理解的状态；客户端与服务端任务都要避免无限重试。

## 16. 可观测性、灰度与回滚

### 16.1 监控

| 类别 | 重点指标 |
| --- | --- |
| API | 错误率、延迟、权限拒绝、限流 |
| 发布 | 成功、明确失败、未知结果持续时间、幂等冲突 |
| 媒体 | 上传和处理失败、孤儿对象、回收失败 |
| 查询 | 慢查询、扫描量、空页、游标异常 |
| 同步 | outbox 积压、重试、补拉失败、版本失效 |
| 通知 | 可见未读数与列表不一致、重复事件 |
| 客户端 | 账号串写拦截、旧响应丢弃、任务恢复失败 |

日志使用 operationID、clientRequestID 和资源 ID 关联，避免打印 token、私密正文和完整选人名单。上线前指定各指标的负责人和告警阈值。

### 16.2 数据库迁移

迁移版本化，先新增表和字段，再部署兼容代码；需要回填时先完成并验证约束，最后启用功能。上线前验证备份及恢复路径。

现有内存隐私设置不能直接当作可信服务端设置；第一次接入读取服务端结果。需要导入本地设置时须用户明确提交。参考仓库中的缓存、假数据和草稿不自动迁移成正式动态。

### 16.3 发布与回滚

服务端和客户端按账号灰度，先内部多人测试，再小范围放量。能力开关分开控制发布、互动、视频及读取。

回滚优先关闭有问题的能力，保留已保存数据和严格授权；不回退到更宽松的隐私实现。生产故障需要能暂停发布、恢复 outbox、校准关系投影和修复媒体回收。

| ACL-07 | 非好友点赞评论 | 列表、计数、分页、通知和写响应都不显示 |

| ACL-15 | 回复目标已删除且仍为可见好友 | 只返回经授权的目标 ID，显示匿名占位，无原姓名头像正文 |
| ACL-16 | 删除目标缺失身份、非好友或关系未知 | 隐藏整条回复及相关通知，删除标志不能授予访问权限 |

### 17.2 发布、一致性与生命周期

| 编号 | 场景 | 预期 |
| --- | --- | --- |
| PUB-01 | 并发提交相同发布键 | 只有一个资源，返回同一结果 |
| PUB-02 | 同键不同内容 | 返回冲突 |

| PUB-04 | NOT_FOUND 后迟到原请求 | 同键约束仍防止重复 |
| PUB-05 | 两个任务绑定同一媒体 | 仅一个成功，另一个明确失败 |

| PUB-07 | 清理任务与发布并发 | 不删除已绑定对象 |
| PUB-08 | 点赞快速切换和乱序 | 最终状态符合最后意图，无重复通知 |
| PUB-09 | 账号或服务器切换 | 无串号响应、草稿或媒体展示 |
| PUB-10 | 页面返回、dispose、前后台变化 | 无重复订阅、已销毁页面写入或草稿丢失 |

### 17.3 分页、通知与上线

| 编号 | 场景 | 预期 |
| --- | --- | --- |
| SYNC-01 | 同毫秒或同数据库时间发布多条 | 不因精度截断漏项 |
| SYNC-02 | 大量不可见动态夹在列表中 | 不提前到底，不无限空页加载 |
| SYNC-03 | 不可见评论很多 | 可见数量和分页一致 |
| SYNC-04 | 刷新期间旧加载更多响应返回 | 不污染新列表 |
| SYNC-05 | 已读到 100，同时到达 101 | 101 保持未读 |
| SYNC-06 | 通知操作者变为非好友 | 通知项和未读一起过滤 |
| SYNC-07 | 事件重复、乱序、断线或进程崩溃 | 可重试并最终恢复服务端状态 |
| SYNC-08 | 删除、下架后的旧通知 | 无原文、身份和图片泄漏 |
| RELEASE-01 | 亮暗主题及 Android / iOS | 正常和异常状态均可使用 |
| RELEASE-02 | 数据迁移、能力灰度与回滚 | 可验证、可停用，不放宽权限 |

测试使用至少作者、两名关系不同的好友和一名非好友，交叉验证不同查看者的互动数量。自动化重点覆盖权限、并发、幂等和分页；设备验证覆盖媒体、生命周期、主题和平台行为。
