# 大账号恢复同步优化（2026-10-10）

## 修改范围

- 会话列表继续由 OpenIM SDK 提供，不再随整页会话更新，额外查询该页所有群的功能元数据。列表复用现有 `GroupLiveListScope`，只在群头像进入活动视口后发起元数据查询。
- `GroupFeatureStore` 区分 SDK 已推送的群和界面实际使用过的群。前台恢复、SDK 同步完成时，只为后者补查元数据；SDK 仍正常接收全部群资料、成员和消息更新。打开过的群功能上下文仍能收到重连事件。
- 普通群首次返回空功能元数据时，不发布虚假的功能变化事件，避免列表再发一次 `live/current` 请求。有效功能变更、功能移除和损坏数据仍走现有处理。
- 本工作区已有的首页先展示本地会话、再清理旧服务会话，以及区分“连接中”和“同步中”的修改一并保留。
- 服务端 `BatchGetIncrementalGroupMember` 按最多 100 个群，批量读取实际操作者的成员关系、群状态和版本；版本一致的群直接返回原协议规定的空增量。有变化、未知版本、权限异常和批量查询失败都保留原逐群校验路径。响应顺序和 500 条变更预算不变，没有修改客户端 SDK、数据库结构或协议。

## 服务端实测

样本为反馈账号的 3115 个已加入群，使用同一份最新版本快照，连续执行 3 轮、每轮 7 个请求。通过本机 RPC 使用该账号的实际成员权限读取；没有登录该账号、发送消息或清理缓存。

| 群成员版本核对 | 第 1 轮 | 第 2 轮 | 第 3 轮 |
| --- | ---: | ---: | ---: |
| 修改前 | 1328.274 ms | 1285.454 ms | 1320.123 ms |
| 修改后 | 154.289 ms | 135.334 ms | 134.243 ms |

中位数从 1320.123 ms 降至 135.334 ms，耗时减少 89.75%。每一轮均覆盖 3115 个群。修改前后的完整响应一致；修改后逐群调用原单群接口校验，3115 个结果全部一致，校验期间没有版本变化。

另通过现有 HTTP API 核对服务发现已切换到新服务：全账号三轮分别为 160.75、159.43、164.71 ms，全部请求成功。该路径使用管理员身份，不能与上表用户权限的 RPC 耗时混为一组。

这些数字只表示已有版本、群没有变化时的服务端核对成本，不包含手机网络、本地数据库加载、离线消息补齐和界面绘制，也不代表首次安装的全量同步。当前没有该手机修改后的完整恢复耗时。
