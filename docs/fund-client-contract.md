# 红包和转账客户端合同

实现依据 2026-10-03 下载的 [前端资金文档](http://8.217.191.236:10018/client/fund.md)、[业务规则](http://8.217.191.236:10018/fund.md) 和 [服务端实现说明](http://8.217.191.236:10018/fund-impl.md)。文档副本保存在工作区 `.temp/wallet-api-docs`，最新前端合同保存为 `current-fund-client.md`。实现说明内部仍有旧错误码和五字段消息描述，客户端以最新前端文档的 `remark`、参数错误 `1001` 及资金错误 `20026`–`20038` 为准。

## 数据与认证

- 资金接口使用现有 Chat 地址 `Config.appAuthUrl`，请求头 `token` 使用 `DataSp.chatToken`，不使用 IM token。
- 币种代码是 `USDT`、`TRX`、`BI99`；`BI99` 在界面显示为 `99BI`。
- 所有金额在请求和响应中使用十进制字符串。`FundAmount` 使用 `BigInt` 最小单位，USDT/TRX 支持 6 位小数，99BI 支持 2 位，不经过浮点数转换。写入请求拒绝金额或普通群红包总额超出 int64 的情况。
- 余额由 `GET /chat/fund/balances` 获取；缺失币种或非法数据作为错误处理，不补造余额。
- 支付密码状态和设置复用现有 `OpenIMProfileService` / `TradePasswordPage`。写入请求使用 `payPassword` 原始 6 位数字，不把它当登录密码进行 MD5 转换。

## 发出和领取

| 业务 | 请求金额 | 收款对象 | 行为 |
| --- | --- | --- | --- |
| 单聊转账 | `amount` | `recvID` | 直接到账 |
| 群转账 | `amount` | `recvID` + `groupID` | 指定一名当前群成员，直接到账 |
| 单聊普通/专属红包 | `amount` | `recvID` | 直接到账 |
| 群专属红包 | `amount` | `recvID` + `groupID` | 指定一名当前群成员，直接到账 |
| 群普通红包 | `shareAmount` + `shareCount` | `groupID` | 总额等于每份金额乘份数，需要领取 |
| 群拼手气红包 | `amount` + `shareCount` | `groupID` | 总额最小单位数至少等于份数，需要领取 |

`POST /chat/fund/packets/:orderID/claim` 不带支付密码。领取响应只保证金额，不代表客户端已经刷新到账余额。发送人允许领取自己发出的群普通或拼手气红包；群成员资格、份额、过期、退款和限额由服务端判定。客户端不会实现本地分配或本地退款。

资金单通过 `GET /chat/fund/orders/:orderID` 获取。`status` 为 `done`、`open` 或 `refunded`。客户端读取份额的 `claimerID`，以服务端订单作为权威状态。

### 订单发送人兼容

2026-10-03 从已登录测试设备只读核对真实单聊普通红包和群转账：GET 均成功，`data.order` 的单号、业务、币种及金额与对应资金消息一致，但没有 `senderID` 或 `sender_id`。旧详情校验把发送人当作必填，导致双方都看到「订单信息不匹配或不完整」。

详情兼容服务端未返回发送人的订单，仍校验单号、业务、币种、精确金额、场景、收款人、状态及群红包份额。接口提供发送人时保留原身份交叉检查；接口缺少该字段时，读取授权由带 Chat token 的订单 GET 决定，领取资格继续由领取接口判定。不会从消息内容补造 API 订单身份、余额或到账结果。

发送人头像和昵称可回退到同一条 OpenIM SDK 消息的发送者资料。回退资料只用于展示，且必须匹配当前资金消息的单号、业务、币种和金额；接口中的发送人身份优先，没有可靠资料则显示通用发送人文案。SDK 元数据不作为付款、到账或领取授权依据。回归样本仅保留真实响应结构及字段类型，使用测试单号和用户 ID，不包含设备凭据或真实聊天内容。

## 祝福语和备注

- 红包发送页支持祝福语，转账发送页支持备注；两种请求都通过 `remark` 字段提交。`FundRemark.normalize` 先去掉首尾空白，再以 `String.runes` 校验最多 12 个 Unicode 码点；标点、组合字符和 emoji 序列中的每个码点都计入，不按 UTF-16 长度或视觉字符数计算。超长输入在请求发出前拒绝，服务端参数错误 `1001` 也显示具体提示。
- 明确提交空字符串时，红包由服务端写入默认祝福「恭喜发财，大吉大利」，转账保存空字符串。客户端显示服务端返回的实际值，不把本地占位提示当作已经保存的内容。
- `FundApi.sendPacket` / `sendTransfer` 的 `String? remark` 保持可选：`null` 时省略字段，显式传入 `''` 时提交空字符串。旧待确认记录没有 `remark` 时继续发送原请求体，不在恢复或重试时补入新字段。
- `FundOrder.remark` 兼容旧订单缺省为空字符串；已提供的字段必须为字符串。详情和聊天卡片以 GET 得到的订单备注为权威，旧消息缺少备注仍可打开；空红包展示默认祝福，空转账不增加备注行。
- 同一 `clientOrderID` 的备注以服务端第一次写入为准。返回备注与本次请求不同，不代表发生了第二笔付款，也不参与金额、收款人等付款身份校验；不能因此新建订单或再次扣款。

## 幂等与消息

- 每笔付款在发出前生成 UUID v4 `clientOrderID`。付款超时后使用同一个编号和原来的业务字段重试；不能把超时当作扣款失败后再新建一单。
- 成功响应至少需要真实 `orderID`；仅返回 ID 时，客户端继续 GET 获取完整订单。响应的币种、金额、场景、业务，以及已提供的客户端单号和收款对象必须符合原请求。
- 超时、成功响应不完整或成功后确认订单失败会返回 `FundApiException.isUncertain == true`，供页面保留原编号并确认。
- 曾经待确认的交易在重试时，即使返回支付密码错误、锁定或其他业务拒绝，仍保留原单号和请求。文档没有约定服务端支付密码校验与幂等查重的先后顺序，重试拒绝不能证明原来的请求未提交。只有首次请求的确定拒绝可清掉该失败单；待确认交易必须由同单号成功确认后才能结束。
- 同一聊天和业务下的待确认交易按账户和服务地址持久保存。并发页面不能替换原交易，同号也不能更改业务字段；祝福语和备注随原请求冻结，恢复后不能修改。清除操作必须匹配原 `clientOrderID`。
- 服务端资金提交成功后负责发 OpenIM `contentType=110` 自定义消息，失败由服务端补发。客户端不会再次发送一条资金卡片。
- 卡片 JSON 携带 `orderID`、`biz`、`currency`、`amount`、`status`、`remark` 六个字段。转账业务识别 `transfer` 和 `group_transfer`；旧消息缺少第六个字段时兼容空备注，非法的可选备注不丢弃资金卡片。打开卡片后必须重新查询订单，并以订单中的备注更新展示。

## 产品实现与使用入口

入口为聊天页面「+」工具箱中的「红包」和「转账」，群聊中转账选择一名当前成员。资金卡片不可撤回：移除一条聊天消息不会撤销已经完成的资金交易。

本轮补齐现有红包和转账的祝福语、备注与展示链路，不新增数字资产、闪兑或提现页面。

对照本地 99chat 钱包模块的业务入口、三种群红包、选人、支付和订单详情行为。当前后端的直接到账规则优先于参考项目旧版收款确认逻辑。

复用现有聊天头像、时间轴、菜单、消息点击链路、`SearchBox`、`SettingsEmptyState`、`TradePasswordPage`、共享密码组件和 `AppTokens`。资金卡片按 99chat 使用 40pt 圆形来消息头像，发出的卡片不显示头像；卡片底栏显示实际发送时间，保留聊天时间轴。新增发送页、详情页、单选群成员页、资金卡片、API/金额模型及待确认存储，因为当前 OpenIM 客户端没有对应的资金业务能力。未替换 SDK、会话管理或路由框架。

新增界面支持 Light/Dark、横屏、小屏和大字体。群成员列表沿用 SDK 的分页和搜索；详情以批量 SDK 昵称显示参与者。工具箱空间不足时可以滚动，资金状态按账号和服务地址隔离，异步响应不能覆盖另一个会话身份的状态。
