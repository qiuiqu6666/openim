## 结论与证据边界

当前前端把业务码 `20056` 映射为“收藏原件不可用”；用户本次失败的数字码尚未捕获。不能仅凭文案认定本地文件或物理存储已删除。现已确认两个独立问题：

1. 生产服务仍返回 `http://localhost:10005/...` 的签名上传地址，手机会连接自己的 localhost。上次准备的公网 signer 补丁和配置尚未加载。这是确定的客户端上传阻塞。
2. 前端已经完成上传、随后 CREATE 明确返回 20056 时，旧逻辑保留失效 asset/uploadID。再次添加相同原件继续复用该资产，可能反复失败。本次已修复这一确定的恢复漏洞。

**目前没有留存到用户本次失败请求，不能确定其 20056 发生在 COMPLETE 还是 CREATE，也不能认定用户实际命中了第二条缓存漏洞。**两个设备的有限日志中未检出该错误；只读缓存中未观察到完成资产缓存。服务器日志缺少对应底层错误，尚不能排除瞬时上传状态或数据库异常。

服务端签名配置必须部署后才能在手机验证上传。隔离测试成功与前端修复成功，不等于生产媒体功能已恢复。

## 分阶段理解 20056

当前部署源码的媒体路径为 init → PUT → complete → create：

| 失败阶段 | 已核实的含义 | 本次前端处理 |
| --- | --- | --- |
| 本地读取 | 文件不存在、不可读，且没有可恢复的已上传／完成记录 | 提示“本地原文件不可用，请重新选择图片或文件” |
| COMPLETE 20056 | 当前 owner 下找不到 upload reservation | 明确拒绝后严格清理会话，下次主动重新选择／上传 |
| COMPLETE 20066／未知网络结果 | 可能是暂时故障或结果尚未确认 | 保留原上传 ID 和请求编号 |
| CREATE 20056 | 上传 ID 没有可用完成映射，或引用资产不满足归属／ready 校验 | 旧 CREATE 明确终结且持久记录清理成功后，清理失效资产；下次添加重新上传 |
| CREATE 未知／取消／20066 | 未取得确定结果 | 保留原正文、资产及请求编号，继续核实 |

当前服务端 reservation 存在但已过期／非 pending，以及对象读取或内容检测失败，各有其他错误路径，不能全归入 20056。COMPLETE 中忽略 FinishUpload 持久化错误仍是需要失败请求证据核实的可能性，本次没有把它当作已证实根因。

## 本次前端改动

### 添加媒体的恢复

- `lib/services/favorite_repository.dart` 的 `createMedia` 只在确定 CREATE 20056 后启动资产失效清理。先确认原 outbox 与 CREATE 身份已终结，再严格保存媒体检查点清理结果。
- 清理包括 asset、session、uploadID、uploaded 状态和 init／complete 请求编号。失败动作中不自动重建，不在同 UUID 下更换正文；下一次用户主动添加才重新上传并使用新编号。
- 检查点保存失败时恢复原媒体任务和 init／complete 编号，提示设备保存失败。终结回执未保存、未知结果或账号切换时不丢弃原资产。
- 同一严格清理方法也接入重启后的 outbox 自动补交：先前结果未知、随后 CREATE 明确 20056 时，一并清除匹配该请求正文的失效资产，下一次主动添加可直接重新上传。只清理同媒体动作、同 uploadID 与 assetID，不影响文字创建或其他原件。
- `lib/pages/favorites/data/favorite_media_upload.dart` 对确定 COMPLETE 20056 的清理也加入严格持久化及回滚。未知／取消结果不会被当作确定失败。
- 缺少本地原件时，只允许已有完成资产或已确认 PUT 的记录恢复。只有 reservation、尚未上传的记录必须重新选择文件。
- 公共终结判断同时检查 `isUncertain` 和 `isCancelled`，避免数字错误码意外清除尚待确认的请求。

### 另行发现的归档重试响应兼容

部署的 retry-archive 成功响应是 `{jobID, status}`，不是 `{item}`。已新增独立任务确认 DTO 与恢复模块，仓储仍通过正式详情 GET 返回 FavoriteItem：

- 确认回执按账号、动作和原 UUID 严格持久保存，恢复正文不变。
- 已持久保存回执，或当前进程仍保留回执时，详情读取失败只补读详情，不重复 POST。
- 老版本没有回执时先读状态；已经 pending／ready 不再次提交。
- 确认保存失败时保留原编号和进程内回执，账号变更守护阻止迟到确认污染其他账号。

该兼容修复与本次“添加图片／文件”的主诉分开。旧服务端归档重试缺少完整持久幂等机制：如果确认无法保存、进程重启且任务已再次失败，客户端不能单独保证跨进程 exactly-once，不宣称已经解决这一窗口。
