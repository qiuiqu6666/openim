# 最新窗口恢复与有限缓存

2026-10-14。适用原生 SQLite Core（Android/iOS/桌面）；Flutter 聊天恢复同步调整。

## 行为

- 普通消息重连/前台校准自动恢复服务端最高 Seq 附近最多 100 个位置。缺少序号须有实际消息或服务端可见边界依据，空列表不视为完成。
- WebSocket 普通消息无需等待旧缺口。重复序号及已交付区间去重；落库和消息/会话事务成功后才确认区间。
- 通知流继续按序恢复：撤回、成员状态、读回执等不属于可选旧历史。
- 无锚点历史查询确认服务端最新位置；带锚点查询按需分页。每次最多 100 条，并限制删除密集区间的递归扫描；扫描预算耗尽返回可重试错误，不伪造历史结束。
- Flutter 恢复只刷新一页最新消息，最多两次延迟重查，不循环向前追赶旧缺口。在历史窗口中保持原位置，用户选择翻页/返回最新。

## 检查点

`sdk_message_coverage_v1` 保留向后兼容的 `completed`、`target` 并增加 `covered`。

- `target` 是观察到的服务端目标，不能证明本地完整。
- `completed` 是连续交付/可信不可见前缀，独立于本地缓存最高序号。
- `covered` 合并已成功交付的离散区间，最多保留最新 100 个离散区间。
- 最新窗口内 `target - covered - completed` 的补集是自动恢复任务；更早补集是按需历史，不是后台下载任务。
- 内存正在执行的请求不作为完成证据。进程重启重新从持久化目标及区间推导未完成的最新窗口；数据提交后、检查点提交前退出会安全重放。
- 缓存淘汰不改变交付检查点。上滑依据本地实际行与服务器重新取回缺失内容。

示例：连续 100、服务端 1000，自动拉 901–1000 后仍是 `completed=100`、`covered=[[901,1000]]`。101–900 留在服务端，需要时才请求。

## 原生缓存及状态

`pkg/db/message_cache.go` 中的默认预算：每会话 1,000 条、每账号 20,000 条、约 64 MiB 消息内容及元数据估算，任一超限触发 LRU 淘汰。分页访问更新使用时间；保留最多 20,000 个普通淘汰锚点，每个会话/视图另保留两个当前翻页位置，防止持续实时流量淘汰正在使用的分页位置。这些位置只含 ID、Seq 和时间。

限制针对有服务器 Seq 且已成功发送的可替换消息。待发送/失败/尚未拿到 Seq 的消息、必要删除标记、撤回覆盖记录和读水位不计入正文预算。预算不是数据库文件物理大小上限，也不是媒体目录限额。SQLite 释放的页供后续复用，不在热路径执行 VACUUM，不下载历史媒体原文件。未缓存历史不能离线浏览，本地搜索只搜索尚存内容；更早内容需服务器仍保留且用户仍有权限。

新表采用增量迁移，不清空数据库。升级时逐会话接管已有普通消息缓存，再执行预算清理；特别大的旧本地数据库应单独量测首次启动迁移耗时。普通收取、发送确认及历史读取后维护缓存，失败保留已交付消息并在后续访问重试，故失败/中断期间允许短暂超过预算。

撤回先保存独立 Seq 覆盖记录，未缓存原消息不会卡住通知流，未来拉取再次套用撤回状态。缓存淘汰保留会话摘要及未读；未读按服务端 MaxSeq/HasReadSeq 校准，最新窗口被实时消息填满时仍执行必要校准。最新页预取先于实时推送落库时，仍按交付/读水位计入一次未读，不把缓存存在当成交付完成。累计读水位独立保存，淘汰再拉取保留已读状态。群组旧读回执不得清除更晚未读或恢复已清除的未读。
